# データの守り方（運用メモ）

「お口の観察ログ」で預かるデータをどう守っているか、何が弱点か、何を定期的にやるか。

---

## 1. いまの守りの仕組み

### 3段の関門

| 段 | 仕組み | 効果 |
|---|---|---|
| 1 | RLS（行レベルセキュリティ） | ログインしても**自分の行しか**読み書きできない |
| 2 | 匿名キーからの遮断 | ログインしていない人は**何も読めない** |
| 3 | 管理画面用の匿名ビュー | 集計に `user_id` を**そもそも含めない** |

### 実測で確認済みのこと（2026-08-07）

- 匿名（anonキー）で `records` / `profiles` / `organizations` / `admins` を読む → **すべて0件**
- 匿名で書き込み → **401**
- ログイン済みアカウントで全記録を要求 → **自分の分だけ**返る
- 同アカウントで他人の `profiles` を要求 → **0件**
- 同アカウントで管理者用ビューを要求 → **0件**

### 個人が特定されにくくする配慮

- 管理画面の集計は母数が5件未満なら数値を出さない
- 配布IDは10桁のランダム（約820兆通り）で、団体名・種別・時期が読み取れない

## 2. 弱いところ（把握しておくこと）

### 🔴 バックアップが無い（最大のリスク）
無料プランには自動の巻き戻し機能が無い。**誤って `delete` を実行すると復旧できない。**
→ 対策：`backup-export.sql` で定期的にCSVへ書き出す（下記）。

### 🟠 Supabase管理画面のアカウントが全ての鍵
ここにログインできる人は RLS を無視して全データを見られる。
→ 対策：**二段階認証を必ず設定する。** 共有アカウントにしない。

### 🟠 `service_role` キー
これが漏れると全データにアクセスされる。アプリのコードには置いていない。
→ 対策：どこにも貼らない。漏れた疑いがあれば即ローテーション。

### 🟡 保存期間の定めが無い
記録は消さない限り残り続ける。
→ 将来的に「◯年で削除」の方針を決める。

### 🟡 管理画面の閲覧履歴が残らない
誰がいつ集計を見たかの記録が無い。

---

## 3. 定期的にやること

| 頻度 | 作業 |
|---|---|
| 週1回 | `backup-export.sql` でCSVを書き出して社内保管 |
| 配布・イベント直後 | 同上（データが増えた直後は必ず） |
| 随時 | 退職・異動時に `admins` から削除 |
| 年1回 | 管理者一覧の棚卸し、パスワードのローテーション |

---

## 4. 個人情報を増やすときの注意

住所・氏名など、より重い個人情報を扱う場合は**コードだけでなく体制の整備が必要**になる。

追加する前に決めること：
- **何のために使うか**（目的を超えた利用はできない）
- プライバシーポリシーの改定（取得項目・目的・保管期間）
- 利用者への**明示的な同意**の取り方
- 保管期間と削除の手順
- 事故が起きたときの連絡体制・責任者

技術面で最低限そろえること：
- バックアップの仕組み（上記が未整備のまま重い情報を預からない）
- Supabaseアカウントの二段階認証
- アクセスできる人を必要最小限にする
